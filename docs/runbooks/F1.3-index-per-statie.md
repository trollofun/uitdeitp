# Runbook F1.3 — unicitatea reminderelor devine per stație

**Status: PREGĂTIT, NEAPLICAT.** Este singura migrare breaking din PRD-ul uitdeITP. Se execută în fereastră proprie, niciodată împreună cu alt deploy.

## Ce schimbă

Azi indexul unic e global: `(guest_phone, plate_number) WHERE deleted_at IS NULL`. Consecință — dacă același client se înregistrează la stația B, reminderul stației A e șters soft: **ultima stație fură clientul**.

După migrare, cheia devine `(station_id, guest_phone, plate_number)`: fiecare stație își păstrează clientul. Regula de precedență la notificare (expirarea cea mai recentă câștigă) e deja implementată în `src/lib/services/reminder-dedupe.ts`, sub flag.

**Efect vizibil pentru șofer:** dacă e înregistrat la două stații pentru aceeași mașină, va primi două SMS-uri per interval. E comportamentul dorit comercial (fiecare stație plătește din creditul ei), dar trebuie asumat explicit.

## Precondiții

1. Rulează `supabase/migrations/prepared/F1.3/01_analysis.sql`.
2. **Abort dacă interogarea (1) întoarce rânduri** — există coliziuni sub cheia nouă; rezolvă-le întâi.
3. Baseline măsurat pe 2026-08-07: 0 coliziuni, 1 reminder guest fără stație, 90 remindere guest active. La aceste dimensiuni, construirea indexului durează secunde.
4. Backup / point-in-time recovery confirmat activ.

## Execuție (5 comenzi, una câte una)

`CONCURRENTLY` nu poate rula într-o tranzacție — se execută fiecare separat prin `mcp__supabase__execute_sql` sau din SQL editor, nu ca fișier de migrare.

| # | Comandă | Așteptat |
|---|---|---|
| 1 | blocul `DO` de la secțiunea A din `02_migration.sql` | `NOTICE: Precondition OK` |
| 2 | `CREATE UNIQUE INDEX CONCURRENTLY ... idx_unique_active_station_guest_reminders` | success |
| 3 | `CREATE UNIQUE INDEX CONCURRENTLY ... idx_unique_active_guest_no_station` | success |
| 4 | `DROP INDEX CONCURRENTLY IF EXISTS idx_unique_active_guest_reminders` | success |
| 5 | interogarea de verificare (secțiunea E) | exact 2 index-uri `idx_unique_active*` |

Dacă pasul 2 sau 3 eșuează, indexul rămâne `INVALID`: șterge-l (`DROP INDEX CONCURRENTLY`) și reia — **nu trece la pasul 4**.

## Flip-ul de aplicație

După SQL: `DEDUPE_SCOPE=per_station` în env-ul Vercel al proiectului `uitdeitp` + redeploy. Codul suportă deja ambele valori; nu se modifică nicio linie.

## Smoke test (obligatoriu)

1. Kiosk pe stația proprie: trimite o placă nouă → reminder creat.
2. Retrimite același telefon+placă la **aceeași** stație → reminderul vechi devine superseded, unul singur rămâne activ.
3. `select id, station_id, deleted_at, superseded_at, superseded_by from reminders where plate_number='...' order by created_at;`
4. Cron real a doua zi: `select count(*) from notification_log where created_at::date = current_date;` — nu scade brusc.

## Rollback

`03_rollback.sql`, în ordine: pasul A (alege câștigătorul per pereche — necesar, altfel indexul global nu se poate recrea), apoi B și C, fiecare separat. La final `DEDUPE_SCOPE=global` + redeploy.

## Abort dacă

- analiza (1) întoarce rânduri și nu ai timp să le rezolvi în fereastră;
- vreun `CREATE INDEX CONCURRENTLY` rămâne blocat peste 5 minute (tranzacție lungă în paralel);
- cronul zilnic rulează în următoarea oră (07:00 UTC) — așteaptă să treacă.
